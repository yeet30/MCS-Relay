01The short version

  • Your diagnosis of the lock problem was right. On Google Drive only a file's owner can delete it; everyone else can only change it. Your idea of emptying such files and letting the owner's app delete them is now how the app deletes. It needed no shared list: each emptied file carries a hidden tag, and the owner's app finds its own tagged files with one search (section 02).
  • All 41 findings from Part 1 are fixed, each one listed with where it was fixed and how it was checked (section 07).
  • The app now has the structure from Part 2. One controller owns the hosting session, the lock is held and renewed for the whole session, the sync compares three versions of every file (last sync, this PC, the cloud) and asks before overwriting anything, and an upload only counts once its manifest is written, last.
  • Transfers run in parallel lanes that adapt to your connection and to Google's limits, update files in place instead of re-creating them, and survive a crash: the next start finishes the upload without creating duplicates.
  • Everything that can be tested without your Google account is tested: 466 automated tests, including two simulated PCs taking turns on an in-memory Google Drive that enforces the same ownership rules as the real one. What still needs a real account and a real Minecraft server is listed as a checklist in section 09.
  • 16 commits on main, starting with your own branch, which was saved and merged first. Nothing was pushed (section 10).

02The ownership problem you ran into

You described it like this: you could not delete files that other members had uploaded, but you could change their contents. Your plan was to overwrite such files with nothing, keep a list of them, and let each file's owner delete them automatically the next time they open the app. I checked this against Google's current documentation (pages updated September 2026), and had every claim checked a second time.

What Google's documentation says

QuestionAnswerSource
Can a member delete or trash a file someone else uploaded?No. "Only the file owner can trash a file." Anyone else, even with the Editor role, gets 403 insufficientFilePermissions. This includes the person who created the shared folder.developers.google.com/workspace/drive/api/guides/delete
Can they change its content?Yes. "If you upload a new version of a file owned by someone else, the original owner remains the same."support.google.com/drive/answer/2409045
Can they rename it, tag it, move it?Yes. The roles table allows writers to modify metadata and to move items inside the shared folder (moving needs share rights, which editors have by default).…/api/guides/ref-roles
Who pays for the storage?The file's owner, always. A file you upload into someone's folder counts against your 15 GB; new content you write into their file counts against theirs.support.google.com/drive/answer/9312312
Does a 0-byte overwrite free the space?Practically yes. A file's quota usage is its current version plus versions pinned "keep forever". Older versions are purged within about 30 days. The app never pins versions.…/reference/rest/v3/files (quotaBytesUsed)
Does "Remove" in the Drive website delete it?No. The file moves to its owner's My Drive and keeps using their storage. Other members lose sight of it.support.google.com/drive/answer/7166529

So your diagnosis was exactly right, and so was the core of your idea: a non-owner can empty the file, and only the owner can finish the job. The research added a few improvements, which the rewrite uses.

What changed compared with your plan

  • No shared list. A list file that several members edit would have its own race conditions and its own owner. Instead each placeholder carries an app-private tag (appProperties, visible only to this app), and the owner's app finds its own placeholders with one search.
  • Out of the way, not out of reach. Placeholders are moved into .launcher/pending-delete/, so the world folder stays clean. Unlike the website's "Remove", the file stays inside the shared folder, so every member can still see it and the app can say "3 deleted files are waiting for Alex to open MCS-Relay" (you can see that line in Figure 4).
  • Delete permanently, not to the trash. Trashed files keep counting against the owner's storage for 30 days.
  • Never delete something a manifest still uses. A placeholder is created during an upload, before that upload's manifest is committed. If the owner's app ran its cleanup in that window and the upload then failed, the old manifest would point at a deleted file. The cleanup therefore skips any file the current manifest still lists.
  • Deletions are rare. Every change is written into the existing file (same Drive ID, same owner), so only files that really disappear from the world need any of this.
  • Deleting a whole server. Before trashing the folder, the owner's app tags every file it does not own, so each member's app later deletes their own leftovers instead of Drive silently moving them into their My Drive.

Here is the decision the transfer engine makes for every deleted file. It is the whole rule in one place:

electron/transfer/TransferEngine.ts · deleteRemote() (shortened)const meta = await drive.getMeta(job.driveId);           // 404 → already gone, fine
if (meta.capabilities.canTrash) {                        // I own it
    await drive.trash(job.driveId);                      // 30 days to undo a mistake
    return outcome('trashed');
}
if (meta.capabilities.canModifyContent === false) throw new AppError('FORBIDDEN', …);
await drive.markDeleted(job.driveId, {                   // someone else owns it
    mdhTombstone: '1', mdhServer: job.serverId,
    mdhDeletedBy: me.email, mdhDeletedAt: now,
}, { addParent: pendingDeleteFolder, removeParent: meta.parents[0] });
return outcome('placeholder');                           // 0 bytes, waits for its owner

The old app never deleted anything on Drive. A file you deleted locally stayed in the cloud and came back with the next download.

Things the research found that you should act on

  • Publish the OAuth app. In Google Cloud Console, set the OAuth consent screen's publishing status to "In production". In "Testing" mode every login expires after 7 days. A small group of friends falls under Google's personal-use exception, so verification is not needed; members see a one-time "unverified app" warning, and the project is limited to 100 users over its lifetime. The app now recognises the expiry (invalid_grant) and sends you back to the login page with a clear message instead of failing on every request.
  • A full Drive blocks everyone. When a file's owner is over quota, nobody can change that owner's files. The app now reports this with the owner's name (QUOTA_FULL) instead of failing silently.
  • Storage falls on whoever uploaded first. Most world files are created by the first host, so that person's 15 GB pays for most of the world from then on. Worth knowing when choosing who seeds a new server.

04One session, start to finish

A state machine is a fixed list of phases plus the rules for moving between them. The session controller is one: the Start button only works in idle, Stop only in running (or, while starting, it cancels). That alone makes Part 1's "Stop runs twice" impossible. Each phase the lock should show is written into lock.json, so other members see "Steve is uploading the world" instead of a guess.

What an upload does, and what happens if the app dies at each step

The upload is written so that the app can be killed at any line and the next start still ends in a correct state. The trick is the order: the cloud only "has" a new version once manifest.json says so, and that file is written last. A small journal file on this PC remembers that an upload was started.

#StepIf the app dies right after this step
1Scan the folder and plan against the last sync (base)Nothing was written. The next start plans again.
2Write the journal (this PC, server, base revision, session)The next start sees the journal and finishes the upload before anything else.
3Create missing folders, parents firstThe resumed upload finds them by name and reuses them.
4Transfer: update changed files in place, create new ones (tagged with server and path), delete or leave placeholdersThe resumed upload finds files it already created by their tag and files already updated by their MD5, so nothing is uploaded twice. Other members see "unfinished upload" and wait.
5Read the cloud manifest again; stop if someone else committed meanwhileSame as 4.
6Write the new manifest (the commit)The resumed upload sees a manifest written by this account on top of the journal's revision, recognises its own commit and only writes the base.
7Write the base, delete the journal, release the lockDone. If the release did not happen, the lock simply expires after 45 s.

Steps 4 and 6 have tests that simulate exactly these crashes: "a failed upload commits nothing, keeps the journal, and the retry creates no duplicates" and "an upload whose commit landed before the app stopped is finished, not reported as a conflict".

The lock file is created only by a claim, under the session. The reason the old read wrote, as you explained, was that a stale lock left by someone else could not be deleted. A lock is never deleted now: it is set to free in place, which any member may do, and a new claim overwrites it in place.

Not tested here, by design

No real Google account, no real Minecraft server and no installer build were used: those need your accounts and your PC. Do this once with two Google accounts (A owns the server, B is invited) on two PCs or two Windows user accounts:

  1. Sign in on both

    Allow Drive access. A creates a server, chooses an existing world folder, starts, waits for "Hosting", stops. Check that .launcher/manifest.json appears on Drive.

  2. Invite and join

    A invites B as Writer. B joins with the link, picks an empty folder. B's card should say "First sync on this PC" with the world size.

  3. Take turns

    B starts (download), plays, places a block, stops. A's card should say "B played after you". A starts and sees the block.

  4. The lock

    While A hosts, B's Start is disabled with "A is hosting the server". Kill A's app from Task Manager: after about 45 s B can start.

  5. Ownership

    B deletes a region file that A uploaded, then plays and stops. On Drive the file is in .launcher/pending-delete with 0 bytes. A's card says it waits; when A opens the app it is deleted for good.

  6. Conflict

    Both edit server.properties offline. The second to open sees "Both changed"; choose "Keep cloud version" and check the backups folder (Directory menu).

  7. Crash during upload

    Stop a big world and pull the network cable during the upload. Expect "upload did not finish" with Retry. Close the app, reconnect, open it: the upload finishes on its own and nothing is duplicated on Drive.
