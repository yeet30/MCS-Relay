
=========== RESEARCH Shared drives (formerly Team Drives) as an alternative to My Drive folder sharing 
 (1) No. Google's Drive API guide says plainly that personal @gmail.com accounts cannot create shared drives. The Help Center adds that shared drives are only for work or school accounts, and only when the edition supports them and the admin allows it. The current supported-editions list starts at Business Starter (which got shared drives in September 2024). It also includes Standard and Plus, Enterprise, Education, Essentials, Nonprofits and Frontline Plus. Workspace Individual and Essentials Starter are not listed, and Essentials Starter cannot be signed up for with a gmail.com address. (2) Yes, with conditions. A Workspace org can add outside people with any Google Account as Contributor, Content manager or Manager. That requires sharing outside the organization to be on and the shared-drive setting that lets users outside the organization access files to be enabled. If the org limits sharing to allowlisted domains, users cannot share with personal accounts. The 'Viewer-only' rule applies to the org's own users whose licence lacks shared drives, not to outside members. Business Starter's announcement explicitly says you can add users outside your organization. (3) In a shared drive the organization owns every file, including content uploaded by outside gmail members. The 'owner' role does not exist there, and the owners/ownedByMe fields are not filled in. Storage comes from the organization's pooled quota, not the uploader's own 15 GB. Content managers (fileOrganizer) can move anyone's files to the trash and restore them. Only Managers (organizer) can permanently delete or empty the trash; Contributors (writer) cannot trash at all. My Drive is the opposite: 'Only the file owner can trash a file'. That confirms the author's observation. (4) For a group where everyone uses a free account it is not an option, because nobody in the group can create the drive. It becomes realistic only if one friend pays for at least one Business Starter (or higher) licence: about 30 GB pooled storage per licensed user, price depends on region. That friend creates the drive and adds the others as Content managers or Managers. All uploads then count against that one licence's pool, and the 0-byte placeholder plus 'owner cleans up later' scheme is no longer needed. The app would need supportsAllDrives=true on every files/changes/permissions call. Listing would need corpora=drive with driveId and includeItemsFromAllDrives=true. It would also have to stop relying on owners/ownedByMe and use capabilities.canTrash/canDelete instead. 
-- implications: 1) Shared drives cannot be the default for this app's target group: if all friends use free @gmail.com accounts, no one can create one. Keep the current My Drive folder design as the main path, and treat a shared drive as an optional backend for groups where one member pays for Workspace Business Starter or higher. Starter is the cheapest documented edition with shared drives: about 30 GB pooled storage per licence, regional pricing. That member creates the drive and adds the friends' gmail accounts as Content manager (can trash anyone's files) or Manager (can also permanently delete). The org's external sharing must be On and not allowlist-only; Business Starter defaults its shared-drive settings to allow. 2) In shared-drive mode the ownership problem goes away. Files are org-owned and storage comes from the org pool, so the 0-byte placeholder plus 'pending deletions for the original owner' list is unnecessary there. Deleting becomes PATCH files/{id}?supportsAllDrives=true with {trashed:true}, which works for Content managers. Keep DELETE files/{id}?supportsAllDrives=true only for Managers. Check capabilities.canTrash/canDelete first, and treat 403 insufficientFilePermissions as 'not allowed' rather than a crash. 3) Code changes for shared-drive support: (a) add supportsAllDrives=true to every files.create/update (including uploadType=media/multipart/resumable uploads), files.get (including alt=media downloads), files.copy and files.delete, and to permissions.* and changes.getStartPageToken/changes.list. fileTransferService.ts already adds it on one list call but not elsewhere. (b) files.list should use corpora=drive&driveId=<id>&includeItemsFromAllDrives=true&supportsAllDrives=true. The name-based root folder lookup in googleDriveService.ts (no parents/driveId filter) has to be scoped to the chosen driveId, or the app should store the driveId and root folder ID in config. (c) Do not use owners/ownedByMe/permissions/shared to decide 'who uploaded' or 'who may delete'; these are empty for shared-drive items. Record the uploader in appProperties or the manifest, or read lastModifyingUser/trashingUser. (d) Add a drive picker (drives.list) and a 'mode' flag (myDriveFolder | sharedDrive) in the server config. (e) Plan for the 500k item cap (trashed items count) and the 750 GB/day per-user upload cap; neither is an issue for Minecraft worlds. 4) In My Drive mode the author's observation is confirmed by official docs: only the owner can trash or delete, and editors can only edit content or detach the file from the folder. The owner-side cleanup list is still needed there. Its design (0-byte overwrite versus detach-from-folder, and revision storage) belongs to the My Drive / ownership research area.

=========== RESEARCH Overwriting content of a file owned by someone else (writer role) and Google storage quota, for the "truncate to 0 bytes + owner deletes later" workaround 
 The author's observation matches the docs. In a My Drive folder, a writer (Editor) can modify a file's content and metadata but cannot trash or delete a file they don't own. "Only the file owner can trash a file", and non-owners get insufficientFilePermissions. Replacing content with files.update keeps the original owner ("If you upload a new version of a file owned by someone else, the original owner remains the same"). Storage is always charged to the file's owner, so new content that B uploads into A's file counts against A's quota. A file B creates in A's folder counts against B's quota. For binary files Drive keeps old revisions. An unpinned revision is purged 30 days after newer content is uploaded, or sooner once a file has 100 unpinned revisions. The head revision is never auto-purged. Pinned ("keepForever") revisions, up to 200 per file, are kept and count toward storage. The files.quotaBytesUsed field is defined as "the head revision as well as previous revisions with keepForever enabled". That, plus rclone's docs, suggests unpinned old revisions are not charged, but no consumer help page says so outright. So after a writer truncates a file to 0 bytes, the owner should pay about 0 bytes at once (at most the old bytes for up to 30 days), plus any pinned revisions until someone deletes them. Writers can read revision history. Whether a writer can delete revisions or set keepForever on someone else's file is not documented. Zero-byte files take no bytes but still count as items: there is a 500,000 direct-children limit per non-shared-drive folder (the My Drive root is exempt) and a 500 million created-items limit per account, trash included. Neither matters at this app's scale. One important catch: if the owner is over quota, Google says "nobody can edit or copy your affected files". Other members' uploads to that owner's files will then fail, and the truncation itself may be blocked too (not documented). 
-- implications: 1) The author's workaround works and fits the documented model. Since non-owners cannot trash or delete, a delete issued by a non-owner should be a 'soft delete': files.update (PATCH upload/drive/v3/files/{id}?uploadType=media) with a 0-byte body, then mark the file for the owner's app to remove later. Ownership stays with the original owner. The owner's quota for that file drops to the 0-byte head plus any pinned revisions. Unpinned old revisions appear not to be charged and are purged within 30 days anyway. The behaviour of a 0-byte upload is not documented, so test it. If it fails, use a resumable upload with size 0 or a 1-byte marker.
2) Never pass keepRevisionForever=true. Grep the transfer code and leave it unset. Pinned revisions are charged to the owner (up to 200 per file), and it is undocumented whether a writer can unpin or delete them.
3) Prefer a marker on the file itself over a separate shared list file, which would get read-modify-write races between members. A writer can modify metadata, so set appProperties on the placeholder, for example mdhTombstone=1, deletedBy=<uploader email or id>, deletedAt=<ISO time>. On startup or periodically, the owner's app runs files.list with q = "'me' in owners and appProperties has { key='mdhTombstone' and value='1' } and trashed=false" and calls files.delete on each match. Use files.delete, not trash, because trash still counts toward quota for 30 days. A cleaner variant: also move the placeholder (addParents/removeParents) into a dedicated '_pending-delete' subfolder of the server folder. Writers may 'remove items from the My Drive folder' and 'add items to the folder', so the world tree stays clean. Do not just remove its only parent; per community reports it then lands in the owner's My Drive root.
4) The manifest must record the deletion: a tombstone entry with deletedAt/deletedBy. Downloaders must skip tombstoned entries and must never treat a 0-byte remote file as real data. Downloading a 0-byte region .mca, level.dat or playerdata file would corrupt the world. Key on the tombstone flag, not on size==0.
5) Decide per file at runtime instead of assuming. Request fields=capabilities(canDelete,canTrash,canModifyContent),ownedByMe,owners. If canDelete, delete directly. Otherwise, if canModifyContent, use the soft delete. Otherwise skip and log.
6) Updates should go in place (files.update on the existing fileId whoever owns it), never delete-plus-recreate. Then only true deletions need the tombstone flow, which in a Minecraft world are rare.
7) Show the quota imbalance in the UI or docs. Whoever first created a file pays for all later versions of it, so the folder creator or first uploader pays for most of the world. If that owner goes over quota, everyone's uploads to their files fail. Handle 403 storageQuotaExceeded explicitly and tell the user which owner (from the file's owners field) is full. Truncation may be blocked in that state as well.
8) Item limits are not a practical concern: 500,000 direct children per folder and 500M created items per account. Placeholders still count as items, so the owner-side sweep should run regularly.

=========== RESEARCH OAuth scopes for a multi-user Electron app on Google Drive (drive.file vs full drive, verification, deletion limits) 
 (1) With only drive.file, user B's copy of the app probably cannot read or list files that user A's copy created and shared with B. Google's docs describe drive.file as access to files the app creates, plus files a user opens with the app or hands to it through the Picker. The Picker docs say the grant is for "the user's files". Community reports (rclone, Google developer forums) agree that a file shared with B is not visible to the app until B picks it. No official sentence says this in so many words, so it is medium confidence and needs a two-account test. The Drive API release notes for 2023 through 2026 show no change to how drive.file works. A desktop Picker now exists: it opens in the system browser, only allows drive.file, and has a file_ids filter and an allow_folder_selection option. Google does not document whether picking a folder grants access to the files inside it, and community reports say it does not. (2) The full drive scope is restricted. Google only allows certain app types to use it, and "backup and sync" fits this app. Verification is not required for personal use ("used by only a few users, all of whom are known personally to you"). An unverified app shows a warning screen and is capped at 100 new users over the whole life of the project. A CASA security assessment (renewed at least every 12 months) applies when restricted data is stored on or passed through servers. Google does not explicitly cover a local-only desktop app. In Testing status there is a limit of 100 test users, and test authorizations, including refresh tokens, expire after 7 days. Apps set to In production do not have that 7-day expiry. (3) Yes: files.delete and files.update both accept drive.file, and the consent text says "See, edit, create, and delete only the specific Google Drive files you use with this app". This covers the user's own files that the app has a grant for. (4) No scope lets a non-owner trash or delete a file in My Drive. Google's docs say "Only the file owner can trash a file." So the author's observation comes from Drive's permission model, not from the scope. The scope can only narrow what the app reaches. Editors can upload new content to someone else's file, and the owner stays the same, which is why the 0-byte overwrite works. For this app, the full drive scope, published In production without verification for a small group of friends, is the practical choice. drive.file would make every member pick every file another member creates, which does not work for syncing Minecraft world files. 
-- implications: 1) Scope choice. Ask for https://www.googleapis.com/auth/drive (plus openid, email and profile) once at login. Drop the two-step drive.file-then-drive upgrade, because drive covers drive.file and the two-step flow only adds a second consent screen and token merging that can go wrong. With drive.file only, B's app likely cannot list or download world files that A's or C's app created, even inside the shared folder. Every new file uploaded by another member would have to be picked again by every member through the system-browser Picker. That is unworkable for Minecraft region files that are created all the time. Keep drive.file only as a future option if the storage layout changes to a fixed set of file IDs created once by the host and updated in place, which every member grants once through the desktop Picker's file_ids filter.

2) Publishing status. In the Cloud console, move the OAuth consent screen from Testing to In production and do not submit it for verification. The personal-use exception covers it ("a few users, all of whom are known personally to you"). =========== RESEARCH Deleting, trashing, moving and renaming non-owned files/folders in a shared My Drive folder (Editor/writer role, consumer @gmail.com accounts), Drive API v3, behaviour current as of Oct 2026 
 The author's observation is correct, and Google's current docs (pages last updated 2026-09-03) still say so. In a My Drive folder, a writer (Editor) who does not own a file cannot trash it or delete it. Both files.update {trashed:true} and files.delete fail with 403 insufficientFilePermissions. This also applies to the person who created the shared folder: owning the folder gives no power to delete files that other members uploaded into it. A writer can change a non-owned file's content (uploading a new version keeps the original owner), rename it, change its other metadata, move it within the shared tree, and remove it from the folder. Moving needs permission to share the item, which Editors have by default. Removing a file from the folder does not delete it and does not leave it ownerless: since the single-parent model (enforced from 30 Sep 2020), the file is placed in its owner's My Drive root. It keeps counting against the owner's storage, because only owned files count toward a person's quota. Folders created by another member follow the same rules. When an owner deletes a folder, only the descendants that owner owns are deleted. Everyone else's files inside it are moved to their own owners' My Drive roots. The 0-byte overwrite idea does work technically: a writer may upload empty content, and quotaBytesUsed counts only the head revision plus any revisions marked keepForever. But it leaves placeholder files with real names inside the server folder, and it needs a separate shared list. A cleaner fix uses only documented behaviour. Tag the file with an appProperties tombstone, then remove it from the server folder with removeParents. The owner's app later finds its tagged files with a query and deletes them. Between 2023 and 2026 nothing changed the delete or trash rules for writers in My Drive. The changes in that period were folder-depth and item-count limits, folders with limited access, download restrictions, and quota units from May 2026. Shared drives would avoid the whole problem, but personal Google accounts cannot create them. 
-- implications: 1) Don't create a delete for every content change. Keep the Drive fileId per path in the manifest and update content in place (PATCH upload/drive/v3/files/{id}?uploadType=media). Any writer may do this, and the file keeps its original owner. Real deletions are then needed only when a world file disappears (old region files, removed datapacks, logs).

2) Ask Drive before choosing how to delete. Call GET files/{id}?fields=ownedByMe,capabilities(canDelete,canTrash,canModifyContent,canRename,canMoveItemWithinDrive,canRemoveMyDriveParent),parents,size. If capabilities.canDelete or ownedByMe is true, call files.delete (or set trashed=true if you want a 30-day undo).

3) If the caller does not own the file, recommended over the 0-byte plan: one PATCH files/{id}?removeParents={parentId}&fields=id with body {"appProperties":{"mcdhTombstone":"<serverFolderId>","mcdhDeletedBy":"<email>","mcdhDeletedAt":"<iso>"}}. Per the docs, the file leaves the server tree for everyone at once and lands in its owner's My Drive root. So it no longer clutters listings or name lookups such as name='lock.json', and another client can never download a stale or 0-byte world file. Optionally, upload empty content first in the same pass to free the owner's quota right away. Do it before removeParents, because the writer's access is inherited from the folder and is lost after the removal.

4) Owner-side cleanup on login or app start: files.list with q="'me' in owners and appProperties has { key='mcdhTombstone' and value='<serverFolderId>' } and trashed=false", then files.delete on each result. The query result replaces the separate tracking list, so there is no shared JSON file for several clients to race on. Variant: if the files should stay visible inside the tree, move them into a hidden '.mcdh-trash' subfolder instead. That needs writersCanShare to stay on, so never disable 'Editors can change permissions and share' on the server folder. The owner's cleanup then queries "'<trashFolderId>' in parents and 'me' in owners".

5) If the author's 0-byte placeholder plan is kept anyway, every reader must treat (size==0 && appProperties.mcdhTombstone) as deleted. Otherwise a 0-byte .mca or level.dat gets downloaded and corrupts the world. Name-based queries also need extra filters. Pinned (keepForever) revisions would still use quota.

6) Bug in deleteServerFolder: files.delete on the server folder deletes only the descendants the caller owns. Every other member's files get re-parented into their own My Drive roots and keep using their quota with no warning. Before deleting the folder, tag all non-owned descendants with the tombstone appProperty so each owner's app removes them. Also warn in the UI that other members' storage is freed only when they next open the app.

7) The server creator has no extra rights. Code must never assume the folder owner can delete members' files.

8) Treat 403 insufficientFilePermissions from delete or trash as 'not owner, use the tombstone path' rather than as a fatal error.

9) Rejected alternatives. Per-file ownership transfer to the host sends an email that cannot be turned off, needs the host to accept, and moves all storage to the host. Shared drives need Workspace.

10) Cost: removeParents with tombstone tagging is one files.update (50 units). Cleanup is one files.list (100 units) plus one files.delete per file, far below the per-user limit.

=========== RESEARCH Transferring file ownership between consumer (personal Gmail) accounts through the Drive API v3, and whether it can fix the problem that only owners can delete files 
 (1) Yes. Moving ownership from one personal Gmail account to another is supported through the Drive API v3, but only with the recipient's consent, in two steps. First the current owner calls permissions.create or permissions.update on the recipient's permission with role=writer, type=user and pendingOwner=true. Then the recipient, using their own OAuth token, calls permissions.create or permissions.update on their own permission with role=owner and transferOwnership=true. The old owner is downgraded to writer. Sending role=owner in a single call fails with 403 consentRequiredForOwnershipTransfer (seen in community reports since 2022). (2) Yes. The docs describe the acceptance as an ordinary API call by the recipient, and nothing says a web UI or a click in the email is needed. A community sample from January 2023 runs both steps as code between personal accounts. (3) Emails are sent: to the recipient when the owner creates the pending permission, and to the old owner when the recipient accepts by creating a new permission. They cannot be turned off for ownership transfers (the API returns a 403 if sendNotificationEmail=false is used). Whether the update path skips the emails is not documented. (4) Restrictions: personal to personal is allowed; personal to work/school is not; Workspace accounts can only transfer inside their organisation; no transfers in shared drives; service accounts cannot receive ownership. In the API, the first step itself makes the recipient a writer, so no separate share is needed. Folders can be transferred, but the files inside stay with their owners, so every file has to be transferred on its own. The current docs list no file-type limit, but they don't confirm binary files work either. (5) Yes. Once accepted, the file counts toward the new owner's storage, not the old owner's. (6) Possible in principle, with real costs. Each uploader's app has to start a transfer for every file it creates (only the owner can do that), and the creator gets an email per file. Bulk sharing with emails can hit sharingRateLimitExceeded. All storage lands in the creator's 15 GB. Most important: after consolidation the other members are still only writers, and writers in My Drive cannot trash or delete. So consolidation does not remove the need for the author's 'owner deletes later' queue. It only means one account (the creator) does all the deleting. 
-- implications: 1) Ownership consolidation does not fix the delete problem by itself. Even if every file ends up owned by the folder creator A, members B and C are still writers and cannot trash or delete anything. So a deferred 'owner deletes it later' queue is needed in any design; consolidation only means one account (A) does all the deleting.

2) Recommended design: tombstone plus owner-side cleanup, keeping the author's idea but making it sturdier.
- When an app has to delete a Drive file, it first checks whether it owns it (file.ownedByMe or owners, or capabilities.canDelete/canTrash; these field names come from the File resource and were not re-checked in this research) instead of waiting for a 403.
- If it owns the file, it deletes it with files.delete.
- If not: (a) drop the file from the manifest so no client downloads it again; (b) mark the file itself with a property, e.g. appProperties.mdhDeleted='1' and mdhDeletedAt (writers may change metadata), rather than keeping a separate shared list file, which would have its own ownership and concurrency problems; (c) optionally overwrite the content with 0 bytes, keeping in mind the old revision stays up to about 30 days; (d) optionally remove it from the server folder (writers may 'Remove items from the My Drive folder'), but what happens to a file removed from its only parent is not documented, so test before relying on it.
- On login, each member's app runs files.list with q = "'me' in owners and appProperties has { key='mdhDeleted' and value='1' } and trashed=false" and permanently deletes those files. Both terms are documented query terms.

3) The lock file should never need deleting. Use one lock file, created once by the folder creator. Members take or release the lock by overwriting its content (holder, heartbeat, expiry), which writers are allowed to do. 'Releasing' then means writing an empty or expired state, not deleting the file.

4) If the author still wants ownership consolidation, do it as an optional step and keep it rare.
- Uploader's app: permissions.create(fileId, {type:'user', role:'writer', emailAddress:A, pendingOwner:true}). Expect an email to A per file.
- Creator's app on login: list the server folder with fields permissions(id,emailAddress,pendingOwner,role). For each file where A's permission has pendingOwner=true, call permissions.update(fileId, A.permissionId, {role:'owner'}, transferOwnership=true), with moveToNewOwnersRoot unset so the file stays in the folder.
- Batch slowly and handle sharingRateLimitExceeded and storageQuotaExceeded.
- All world storage then sits in A's 15 GB, which removes the original benefit of spreading storage across members.
- Better use: a one-time 'hand my files to the host' action when a member leaves, not continuous consolidation.

5) The app's full drive scope is already enough for the permission calls (drive.file would also be accepted). Each member's own app has to do its own step, because a member's token cannot accept a transfer for someone else.

=========== RESEARCH Real-world evidence and patterns: deleting files owned by other members in a shared My Drive folder (personal Gmail accounts), and the 0-byte placeholder (tombstone) workaround 
 You described the problem correctly, and it comes from Drive's design, not from a bug in your code. In a folder that lives in someone's My Drive, only the person who owns a file can trash or delete it. Anyone else gets HTTP 403 "insufficientFilePermissions", even with the Editor role. The Drive API guide (updated 2026-09-03) and the Drive Help Center both say this. Editors can still change a file's contents, which is why your overwrite works.

What looks like "delete" for an editor in the Drive web app is really "remove from folder". The file moves to the root of its owner's My Drive, keeps using the owner's storage, and Google calls it "unorganized". Other members lose access to it, because it no longer inherits the shared folder's permissions.

rclone has the same problem. Its issue #3998, open since Feb 2020 and marked "Known Problem", tracks it. The maintainer's proposed fix is to unlink the file with removeParents instead of deleting it. A pull request for that (#9864, Sept 2026) is still open and has not been tested against real Drive. In 2015 rclone could trash files it didn't own; that is no longer possible, and Google doesn't say when it changed. Insync staff described editor deletes as only "un-parenting" the file.

I found no source that describes truncating a file to 0 bytes as a known workaround. It is technically possible because editors can modify content. The documented quotaBytesUsed counts only the current version plus versions marked "keep forever", so a 0-byte overwrite should free the owner's quota right away. Help Center pages don't say whether the storage meter agrees. The main drawbacks are below. The edit fails if the owner is over quota, because Google says nobody can edit that owner's files until they free space. The placeholder still sits in the folder under the same name, so every client must recognise it, or it could download a 0-byte world file. Any pinned ("keep forever") versions still count toward quota.

Two options exist on paper but don't fit. Shared drives would fix this, but they require Workspace (work or school) accounts, not @gmail.com. Moving ownership to the host needs the host to accept each file, and every transfer sends an email that cannot be turned off.

Your idea of a "pending delete" list that the owner's own app processes is the right pattern. Improve it this way: tag every upload with app-private metadata (appProperties), prefer marking or moving the file over truncating it, truncate only to free quota quickly, and have each owner's app also find and delete orphaned files it owns. 
-- implications: 1) Treat "only the owner can trash or delete" as a fixed rule. Before each delete, read capabilities.canTrash and canDelete (and ownedByMe) so the app chooses the right path up front instead of waiting for a 403.
2) Tag every upload, at creation time, with appProperties such as {mdhServer:<serverId>, mdhPath:<relative path>}. Then each owner's app can always find its own files, including orphans that ended up in its My Drive root because someone used the web app's Remove or an older app version unlinked them.
3) When a non-owner needs to delete a file, add a "pending delete" entry to the manifest: {fileId, path, ownerPermissionId/email, requestedBy, requestedAt}. Then mark the file itself with appProperties, e.g. mdhTombstone=1. If renaming or moving is allowed, also move it into a hidden ".pending-delete" subfolder inside the shared server folder. Keeping it inside the shared tree keeps the group's access, avoids cluttering the owner's root, and lets other members check it. Whether an editor can move someone else's file between two folders through the API needs a quick test with two accounts.
4) Make truncating to 0 bytes optional, not the core mechanism. Use it only for large files when canModifyContent is true, to free the owner's quota before they next open the app. Never set keepRevisionForever. Expect it to fail when the owner is over quota, and handle that error without breaking anything.
5) All downloads and sync comparisons must skip tombstoned files, by checking the manifest entry or appProperties and never by size 0 alone. Otherwise a client could restore a 0-byte region or level.dat and corrupt the world. Also ignore the modifiedTime change that the truncation itself causes.
6) On every app start, the owner's app should find its tombstoned files ('me' in owners plus the tombstone flag) and its orphans (its tagged files that are no longer inside the server folder), delete them with files.delete (allowed because it owns them), and remove the matching manifest entries. files.delete is better than trash here, because trashed files keep using quota for 30 days.
7) Use removeParents (unlinking, as the web app does) only as a last resort, guarded by canRemoveMyDriveParent. It hides the file from the group, sends it to the owner's root, and still uses the owner's quota.
8) Don't build on ownership transfer: every file would trigger an email that can't be disabled, and all quota would land on the host. Shared drives aren't available for @gmail.com accounts.
9) Warn about members who leave or go inactive, since their files can vanish. Offer an "adopt" action: the host copies the file (becoming its owner) and puts the original in the pending-delete queue.
10) Packaging the world into fewer, larger files (for example per-region or per-backup archives) reduces how many files someone else owns and so shrinks the problem.
